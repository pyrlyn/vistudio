### T72. Kotlin/JVM hot reload

Requested by the creator ("add kotlin hot reload"), with no further decisions given. Agent choices (reversible; change on the creator's word):

- What it is: recompiled classes are swapped into the running Kotlin/JVM program (the JVM's own class redefinition), Kotlin and Java alike, for every program started through `KotlinDebugCoordinator` (F5, Ctrl+F5, Run | Debug lenses, `.kotlinproj` and `.javaproj`). Triggers as for Flutter (T54): a command (Tools > Kotlin > Hot Reload, `Kotlin.HotReload`) and reload on save (setting, on by default).
- Compilation stays on Gradle (init script, the owning module's `classes` task). The swap is the IDE's part and goes through the JDK (attach mechanism, `Instrumentation.redefineClasses` in a JDK-only agent that the user's Gradle build compiles, like the preview renderer); the debug adapter and the language server are not involved.
- A Gradle daemon for reload compiles only. Measured on this machine (x64 JDK emulated on ARM64, `samples/kotlin-jvm` copy, one-line change): 57 s with the usual `--no-daemon` run, 5-6 s on a warm daemon (37-40 s for the run that starts it). The daemon has a private registry (`-Dorg.gradle.daemon.registry.base`, so no other Gradle client shares it), lives in a process job owned by the session and ends with it; ten idle minutes end it as well. Every other Gradle run stays `--no-daemon`.
- Not chosen: JetBrains' Compose Hot Reload (a Gradle plugin applied to the user's build that needs JetBrains Runtime and covers Compose only; a possible follow-up task); class redefinition through the debug adapter (DAP has no such request, and Ctrl+F5 has no JDWP session); a continuous Gradle build (its file watching is not reliable on network shares, where this repository lives); a daemon shared with the user's own Gradle clients (ending it with the session could break their build).

Probe findings (Eclipse Temurin 21.0.12): an agent loaded with `VirtualMachine.loadAgent` redefines a running class and the program prints the new text; an added method is refused ("class redefinition failed: attempted to add a method") and the old code keeps running; the JVM prints its dynamic-agent warning at every load; with all threads suspended by a debugger (jdb `suspend`, as at a breakpoint) the attach request is not served until `resume`, so a reload at a breakpoint is applied when the program continues; paths with spaces work.

Execution plan:

1. Gradle (`Build/HotReload.gradle`, `Build/VistudioHotReloadAgent.java`): owning module by entry file, `classes` tasks of its main JVM compilations (Kotlin JVM targets and Java source sets), class file lists before the task graph runs and after (the first list of a session with hashes), agent compiled (release 11) and packed outside the project's build folder.
2. Core (`Vistudio.Core/HotReload`): `HotReloadSnapshot` (lists), `HotReloadState` (which bytes the JVM runs; candidates; refused classes stay pending), `HotReloadResult` (agent result, summary), `HotReloadJvm` (the JVM among `jps -l` rows), `HotReloadSession` (compile on the session's daemon, attach client, daemon ended on dispose), `GradleCommand.CreateHotReload`, a shared process job in `OwnedProcess`, setting `HotReloadOnSave`.
3. VSIX: `KotlinHotReload` (session bound to the coordinator's launches, compile through the package's Gradle gate with compiler errors in the Error List, result in the Kotlin pane and the status bar, overlapping requests merged), `KotlinHotReloadSaveListener`, the Tools > Kotlin > Hot Reload command, the option.
4. Checks: unit (`Vistudio.Tests.exe --hot-reload none`, also in the default run), live against Gradle and a JVM (`--hot-reload`), under the installed Kotlin server's debugger through `KotlinJvmLaunch` and `KotlinDapSession` (`--hot-reload debugger`), Visual Studio (`tests/verify-hot-reload.ps1`). Evidence in [docs/hot-reload-validation.md](docs/hot-reload-validation.md); README, architecture and toolchain docs.

Status: steps 1-4 implemented. `./build.ps1` passes (Release build, default run with 1553 assertions, VSIX and icon checks); `--hot-reload none` passes 55 assertions; `--hot-reload` 76 (a Kotlin + Java program under `gradlew run`: body changes in both languages, a refused method addition, the retry after it, a compiler error, a new class, one private daemon ended with the session; 4-10 s per reload after the first, 27 s for the first); `--hot-reload debugger` 74 (through the Kotlin server 271.2085.0: `jps` finds the server-started JVM by its main class, a running debuggee reloads, a reload at a breakpoint is applied on continue, the breakpoint in the reloaded class stops again by itself with the new code, Ctrl+F5 with `vmArgs` reloads and the flag hides the JVM's agent warning). In Visual Studio (`tests/verify-hot-reload.ps1`, EnvDTE, Ctrl+F5): 27 checks pass: reload on save, `Kotlin.HotReload` from an unsaved edit, compiler error in the Kotlin pane and the Error List and its removal, the refused change, command availability, the daemon gone after Stop. Found while checking, outside this task: the Kotlin server's debugger waits only 30 s for the JVM, and on this machine the `--no-daemon` launch needs longer, so F5 in Visual Studio ended before the program started (Ctrl+F5 is not affected); the F5 variant of the script therefore did not get to a reload. Not verified: hot reload in a Visual Studio F5 session, the option page and `.vs\settings.json` key, Multiplatform and Compose modules, multi-module builds, other JDKs, anything on screen. Details: [docs/hot-reload-validation.md](docs/hot-reload-validation.md).

### T71. CPU and memory data while debugging every language

Requested (through the coordinating session): make Visual Studio's Diagnostic Tools window (CPU Usage, Memory Usage, Events, snapshots) work while debugging Kotlin (JVM and the Multiplatform targets), Java, Dart/Flutter, Zig, Rust, C, C++ and WebAssembly; where the window cannot be enabled for a session type, give an equivalent with process CPU/memory of the debuggee plus runtime data where a protocol exposes it.

Probe (Visual Studio 18 Community, ARM64, 2026-11-15; IL of `Microsoft.DiagnosticsHub.VisualStudio.Package.dll` and `VsDebugPresentationPackage.dll`): the Diagnostics Hub starts its debugger session in `PerformanceDebuggerSessionManager.OnDebugProcessCreated` only when `PerformanceDebuggerUtilities.IsPerfDebuggerScenario` finds one of the process's debug engines in a hard-coded allow list (`IsDebugEngineGoodlisted`: native, the managed engines, managed+native, CoreCLR, CLR native compilation); every other engine gets "PerformanceDebuggerDebugEngineNotSupported". There is no registry or MEF extension point for that list (tool factories can only narrow it with `SupportedDebugEngineGuids`). Consequences:

- Rust, Zig, C and C++ F5 launch with `NativeOnly_guid` (`LanguageProjectConfig.LaunchNative`), which is on the list: the Diagnostic Tools window applies to them without Vistudio code.
- Kotlin/Java (engine `7b672d65-...`) and Dart/Flutter (`c4a2e6f8-...`) run on the Debug Adapter Host with their own engine ids, which are not on the list and cannot be added.
- WebAssembly F5 has no debugger (it runs the Run command), so no debug session exists to show the window for.

Agent choices (reversible; change on the creator's word):

- Equivalent for the DAP sessions and WebAssembly: a **Vistudio Diagnostics** tool window (View > Other Windows), opened when such a session starts, with the debuggee's CPU % and memory (working set, private bytes) sampled every second from Win32 process counters, a runtime heap line, an events list (start, break, continue, garbage collections, snapshots, exit) and Take Snapshot with a class-level heap table and the difference to the previous snapshot.
- Runtime data: JVM through the JDK's own tools next to the debuggee's `java.exe` (`jstat -gc <pid> 1000` streaming heap and GC counters, `jcmd <pid> GC.class_histogram` for snapshots; both checked live against a JVM held suspended by JDWP, as at a breakpoint); Dart through the VM service the debug adapter announces (`dart.debuggerUris`): `getVM` gives the program's process id, `getMemoryUsage` the heap, `getAllocationProfile` the snapshot (plain HTTP GET, checked live on a paused isolate). The JVM debuggee is found with `jps -l` (a new JVM whose main class is the launched one), because the Kotlin server starts it through Gradle.
- Not chosen: attaching the native engine to `java.exe` / the Dart VM next to the DAP session to get the real window. A native break (Break All, a native exception) would freeze the JVM's JDWP thread and the Dart VM service while the DAP adapter still waits on them, and HotSpot raises access violations on purpose (safepoint polls, implicit null checks), each one a native debugger round trip. Not chosen either: ETW counters in the Diagnostic Tools timeline (the timeline does not take custom providers; T43's provider stays for the Performance Profiler).
- Creator decision (2026-11-15), replacing T21's F5 message: F5 on a non-JVM Kotlin target (JS, Wasm, Native) runs the target's Gradle run task, like Ctrl+F5, with Vistudio Diagnostics watching the program (WebAssembly's pattern; still no debugger). The other options offered were keeping the message, or launching the Kotlin/Native `.exe` in the native engine. Agent choice: the program is the part of the `gradlew.bat --no-daemon` process tree that is not Gradle itself (`cmd.exe`, `conhost.exe`, `java.exe`, `javaw.exe` left out), so Node (JS, wasmJs) or the mingwX64 executable is measured, not the build. A target without a run task keeps the message; Ctrl+F5 is unchanged.

Execution plan: Core `Diagnostics/` (process counters, usage calculator, session timeline, jps/jstat/class histogram parsers, Dart VM service parsers and client, monitor loop); VSIX `Diagnostics/` (own package and menu resource, tool window drawn in WPF, session hub with debugger mode events) hooked into `KotlinDebugCoordinator`, `DartAdapterProcess` and the WebAssembly F5 path; unit checks `Vistudio.Tests.exe --diagnostics` with live parts against the JDK and the Dart SDK when found; evidence in [docs/diagnostics-validation.md](docs/diagnostics-validation.md).

Status: implemented as planned, including the creator's F5 decision for non-JVM Kotlin targets. `--diagnostics` passes 70 assertions (unit plus live: process tree, JVM running and suspended by JDWP, Dart VM direct and through `dart debug_adapter`), `--diagnostics flutter` 72 (adds a Flutter Windows app through `flutter debug_adapter`), `--diagnostics kotlin-targets` 79 (js, wasmJs and mingwX64 run tasks of the multiplatform sample, only the program counted); the Release build, the default run (1361) and the VSIX checks pass. In Visual Studio (`tests/verify-diagnostics.ps1`, 22 checks, DTE and UI Automation): Dart F5 at a breakpoint shows the Dart VM session in Vistudio Diagnostics (CPU, private bytes, working set, Dart heap, break event; data kept after Stop); C F5 gets Visual Studio's Diagnostic Tools window without a refusal (its charts are not readable through UI Automation). Not run in Visual Studio: Kotlin/Java, Kotlin non-JVM targets, Flutter, WebAssembly, Rust, Zig, C++, Take Snapshot, the dark theme.
